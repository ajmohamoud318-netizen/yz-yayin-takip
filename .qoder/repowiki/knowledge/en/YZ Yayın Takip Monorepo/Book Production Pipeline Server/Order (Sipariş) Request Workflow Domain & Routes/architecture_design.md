Three-layer split inside the module:
- `routes/orders.js` is a Fastify plugin that mounts REST endpoints (`GET/PATCH/POST /order-requests...`) for listing, advancing, rejecting, marking delivery/receipt, starting/cancelling/editing ozalit rounds, requesting change approvals, and saving/approving the `siparis_baski_onay` print-spec form. Every mutating route wraps its work in `withTx`, selects the row with `SELECT ... FOR UPDATE`, delegates state mutation to a pure compute function, then persists via raw SQL, appends an `order_history` row, logs a project timeline entry via `logHistory`, and emits notifications via `services/notifications.js`.
- `domain/orders.js` declares the finite-state machine constants: `ORDER_STEPS`, `ORDER_STEP_OWNER`, `ORDER_STEP_NEXT`, `ORDER_REJECT_TARGETS`, plus labels used by the UI.
- `domain/order-transitions.js` contains the pure state-transition helpers (`computeMatbaaReceive`, `computeMatbaaNotReceived`, `computeMatbaaOnayApproval`, `computeOrderOzalitStart/Cancel/Edit/ChangeRequest/ChangeAccept/ChangeDecline`) that take an order snapshot + actor + context and return `{ order, history }` (or `{ order, advanced, history }` for the multi-party approval). These are intentionally separate from the main pipeline's `transitions.js` so the order workflow can evolve independently while mirroring the same receipt-gate + multi-party ledger semantics.
- Shared utilities in `domain/pipeline.js` (`assertOrderable`, `isAtOrPastStage`) gate whether a project may enter the order flow at all; `domain/errors.js` provides `badRequest`/`forbidden`/`notFound` thrown as HTTP errors.
Dependency direction is strictly one-way: routes → domain transitions → shared pipeline/stages/errors; services layer is only invoked after persistence to emit side effects.
