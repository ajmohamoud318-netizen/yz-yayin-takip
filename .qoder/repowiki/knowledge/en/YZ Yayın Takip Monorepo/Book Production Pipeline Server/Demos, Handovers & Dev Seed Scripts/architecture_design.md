Three sibling files with distinct responsibilities layered on top of shared infrastructure:
- `routes/demos.js` exposes GET/POST `/api/demos` to record designer demo/ozalit form snapshots. The POST uses a transaction (`withTx`) that locks the project row via `getProjectForUpdate` (SELECT … FOR UPDATE) and optionally locks the linked `order_requests` row, enforcing matbaa start-gates before inserting into `demos` and writing a `stage_history` entry through `logHistory`. Reads bypass transactions.
- `routes/handovers.js` exposes GET/POST `/api/handovers` and PATCH `/api/handovers/:id/confirm` implementing the printer→sales handover flow. Role checks gate creation to `printer` and confirmation to `satis`; the confirm path locks the handover row with `FOR UPDATE`, transitions it to `received`, moves the project stage to `satista`, logs history, and fires notifications via `notifyHandoverRequested` / `notifyHandoverConfirmed`.
- `services/seed.js` is a standalone Node CLI (invoked when `import.meta.url === process.argv[1]`) that lazily dynamic-imports `db/seed/users.js` and `db/seed/projects.js` so large seed payloads are absent from the production image; every INSERT uses `ON CONFLICT (id) DO NOTHING` to be fully idempotent.
All routes depend inward on `../domain/errors`, `../db/pool`, `../services/project-repository`, `../schemas/index`, and role-based middleware (`attachUser`); dependency direction is one-way: routes → domain services → DB pool, never the reverse.
