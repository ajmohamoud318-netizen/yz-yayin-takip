The module is split into two sibling folders re-exported through a single barrel `index.js`:
- `constants/` holds pure data: stage enums (`stages.js` with `STAGE_PIPELINE`, `ORDERABLE_STAGES`, `HANDOVER_ELIGIBLE_STAGE`), labels (`labels.js`, `orders.js`), pass kinds (`passes.js`), subtask catalog (`subtasks.js`), and Tailwind color maps (`status-styles.js`).
- `services/` contains stateless pure functions implementing business rules. `pipeline.js` is the core: it reads constants from `../constants/stages.js` and exposes capability helpers (`isOzalitApprover`, `canApproveOzalitNow`, `canMarkDemoStarted`, `canCancel*Request`, `canRejectAtStage`, etc.), guards (`assertOrderable`, `assertNotLegacy`, `assertCanEnterProduction`, `assertHandoverEligible`), and pipeline navigation (`getPipeline`, `getNextStage`, `handoverStageFor`). `progress.js` computes subtask completion percentage and mirrors the server's `subtaskProgress`. `project-status.js` maps `(stage, progress)` to a visual status key and dashboard group.
Dependency direction is one-way: services depend on constants; constants have no dependencies; the barrel `index.js` flattens all exports for consumers. Every service function is deliberately kept in sync with its server counterpart (comments repeatedly cite the matching server file/migration), so the UI can pre-validate actions before sending them to the backend.
