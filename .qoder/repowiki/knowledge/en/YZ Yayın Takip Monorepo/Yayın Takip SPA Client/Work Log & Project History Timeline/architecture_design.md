Three cohesive files split concerns by feature:
- `client/src/hooks/useWorkLog.js` is a plain React hook that owns state for the signed-in user's work-log entries. It fetches via `api.listWorkLog`, performs all mutations (`add`, `edit`, `remove`) optimistically by keeping a `prev` snapshot in closure and restoring it on failure, syncs the auth context's `daily_status` after every change, and splits entries into `today` vs `history` using `todayKey()` and `groupByDay()` from `work-log.js`. It deliberately avoids a Context/Provider because only one consumer (the header pill) needs it.
- `client/src/lib/work-log.js` is a pure constants + utilities module: the `WORK_LOG_KINDS` enum (mirroring the DB CHECK constraint), colour/icon/chip tokens per kind, duration presets, and helpers (`formatMinutes`, `formatClock`, `formatDayLabel`, `todayKey`, `groupByDay`). It also exposes a `WORK_LOG_ENABLED` feature flag that gates the entire feature without touching routes or migrations.
- `client/src/lib/project-history.js` is a pure metadata + transformation library for the project history timeline. It centralises every event type in the `EVENTS` table (with `icon`, `tone`, `weight`, `group`, `label`, optional `noteMode`), falls back to legacy `ACTIONS`/`ADVANCE_*`/`APPROVE_*`/`REJECT_*` tables for pre-migration rows, and exposes functions (`historyMeta`, `buildTimeline`, `truncateTimeline`, `filterCounts`, `dedupeNote`, `rowText`, `hasDemoForm`, `hasOzalitForm`) that turn a flat server list into day-bucketed, folded, filterable timeline nodes. Dependency direction is one-way: the hook imports from both libs; the two libs have no cross-imports.

No UI components live here — this module is purely state management and domain logic consumed by components elsewhere in the client.
