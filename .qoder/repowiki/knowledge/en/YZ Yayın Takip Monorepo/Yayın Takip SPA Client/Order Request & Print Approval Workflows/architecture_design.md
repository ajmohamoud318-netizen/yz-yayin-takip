Two layers compose this module. The `client/src/application/use-cases/orders/` directory holds thin HTTP adapters (`advance-order-request.js`, `create-order-request.js`, `reject-order-request.js`) that wrap `httpClient` calls to `/order-requests` and `/order-requests/:id/advance|reject`; each factory returns a pure function so callers can be mocked in tests (`*.test.js`). State-machine validation is intentionally delegated to the server (`server/src/domain/transitions.js`), so these functions only shape request bodies — they explicitly omit fields like `actor` or conditionally include `assignees`, `route`, `expectedVersion`, `rejectTarget`, and `revizeIds` based on step semantics. The UI layer consists of two React pages: `SiparisListesi.jsx` renders the requester's own order queue (filtered by `requested_by === user.id || 'u-esra'`) with status badges and a mini progress bar derived from `ORDER_STEP_LABELS` and `order_history`; `SiparisOnay.jsx` renders the designer/team-leader approval queue, filtering orders via `isOrderAssignedToDesigner` and `canApproveMatbaaOnayNow`, and orchestrates `TalepSignDialog` and `OzalitFormDialog` to perform in-place updates that are merged back into local state using a shared `belongsHere` predicate. Both pages depend on shared domain constants (`@/domain/constants/orders`) rather than redefining workflow rules.
